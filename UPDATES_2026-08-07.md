# Updates — 2026-08-07

This documents the issues investigated and changes made to `Dad-backend` on this date.

## 1. Re-enquiry was overwriting a rep's lead status

**Reported issue:** Lead "arc 3" (phone `9497211807`) was created, manually moved to status
`interested`, then a second submission for the same phone number came in and the lead's status
was force-reset to `re_enquiry`, wiping the rep's update. There was never a second lead row — the
`Lead` table has a unique constraint on `[phone, organisationId, branchId]`, so a repeat submission
for the same phone always updates the *same* row rather than creating a new one.

**Root cause:** `DuplicateLeadService.handleReEnquiry()` in
`src/services/duplicateLeadService.ts` unconditionally set `status: 're_enquiry'` unless the
existing status was already `new`/`re_enquiry`. Any other status a rep had set — `interested`,
`contacted`, `qualified`, `won`, `lost`, or any org-custom status — got silently overwritten.

This function is shared by **every lead-ingestion path**: manual "Add Lead" (`leadController.ts`),
bulk/CSV import (`leadController.ts`), the public web form (`webFormController.ts`), the public
API (`routes/apiRoutes.ts`), Meta Lead Ads (`services/metaPayloadService.ts`), and Zapier
(`services/zapierWebhookService.ts`).

**Fix (`src/services/duplicateLeadService.ts`):**
- Status is now only auto-set to `re_enquiry` when there's no prior progress to protect (existing
  status is empty, `new`, or already `re_enquiry`). Any other status is preserved as-is.
- `isReEnquiry`, `reEnquiryCount`, `lastEnquiryDate`, the Interaction timeline note, and
  owner/manager notifications still fire in every case — the lead still surfaces on
  `/re-enquiries` (which filters by `isReEnquiry`, not `status`).
- The `LeadHistory` log no longer records a fake `status` transition when status was actually left
  unchanged.

**Status:** Fixed and committed (`fac755d9`, not pushed).

## 3. Meta connection was exposing every Page/Ad Account the Facebook user has access to

**Reported issue:** Connecting `demo@crm.com` to Facebook and selecting only Page
"Worldpassport Skill Academy" (`1207896069067700`) and Business "World Passport Skill Academy 2"
(`916127911516688`) resulted in the `/marketing/ads-manager` Ad Account dropdown showing 3
unrelated ad accounts instead of just the one connected.

**Root cause:** `src/routes/metaAuthRoutes.ts` (OAuth callback) fetched pages via the unscoped
`GET /me/accounts` and ad accounts via the unscoped `GET /me/adaccounts` — both return **every**
Page/Ad Account the connected Facebook user has any role on, across all Business Managers, not
just the ones picked during the consent flow. The same unscoped `/me/adaccounts` call was also
used live by the Ads Manager dropdown endpoint (`marketingController.getAdAccounts` →
`MarketingAPIService.getAdAccounts`).

**Fix:**
- `src/routes/metaAuthRoutes.ts` — at OAuth callback, fetch the Business(es) actually granted via
  `GET /me/businesses`, then fetch Pages and Ad Accounts scoped to those businesses via
  `/{business-id}/owned_pages` + `/client_pages` and `/{business-id}/owned_ad_accounts` +
  `/client_ad_accounts`. Falls back to the old unscoped calls only if no business was granted or
  the scoped lookup returns nothing (keeps existing connections from breaking). The granted
  `businessIds` are now stored on `Organisation.integrations.meta.businessIds`.
- `src/services/marketingAPIService.ts` / `src/controllers/marketingController.ts` — the live
  `/marketing/ad-accounts` endpoint (Ads Manager dropdown) now uses the stored `businessIds` to
  scope its Graph API call the same way, instead of calling bare `/me/adaccounts`.

**Status:** Code changed, not committed. **Important caveat found during verification (see below)
— this fix alone is not sufficient yet.**

### Follow-up finding: `/me/businesses` returns empty without a Business Login Configuration

After disconnecting and reconnecting `demo@crm.com` to test the fix:
- **Pages scoped correctly** — only 1 page ("Worldpassport Skill Academy") was stored. This works
  because Facebook's classic OAuth dialog has a built-in Page picker tied to the
  `pages_show_list` permission.
- **Ad accounts did not scope** — `integrations.meta.businessIds` came back as `[]`, because
  `GET /me/businesses` returned no results for this token. With no business ID to scope against,
  the code fell back to the old unscoped `/me/adaccounts`, so the dropdown still shows multiple
  accounts (and the stored "primary" ad account is now an unrelated one, `CDRC` /
  `act_2000017527533758`).

**Why:** `META_CONFIG_ID` (env var, checked in `src/routes/metaAuthRoutes.ts:39`) is currently
**blank**. Facebook only presents a real "choose which ad accounts / which business to share"
picker — and only narrows what `/me/adaccounts` and `/me/businesses` return — when the app uses a
**Facebook Login for Business Configuration** (a `config_id`, created in the Meta App Dashboard).
Without one, `ads_management`/`business_management` scopes grant visibility into **everything the
Facebook user administers**, with no picker step and no way to narrow it after the fact from
server-side code — this is a Facebook platform limitation for the classic OAuth flow, not
something fixable purely in this codebase.

**Action required (outside this codebase) to fully resolve:**
1. In the Meta App Dashboard (App ID `878997861646422`) → **Facebook Login for Business** →
   create a Login Configuration with asset types **Pages**, **Ad Accounts**, and **Business**
   enabled, with "let people choose which assets to share" turned on.
2. Set that configuration's ID as `META_CONFIG_ID` in the production environment.
3. Reconnect Meta again — `/me/businesses` should then return the selected business, and the
   scoping code already in place (see above) will correctly narrow the ad-account list.

### Related: OAuth redirect URI whitelist error

Separately hit `"redirect URI is not white-listed..."` when clicking Connect. This is a Meta App
Dashboard configuration issue, not a code bug: the `redirect_uri` sent
(`${SERVER_URL}/api/meta/callback`, built in `metaAuthRoutes.ts`) must be added under
**Facebook Login → Settings → Valid OAuth Redirect URIs** (or under the Login Configuration's own
redirect URI list, if using `META_CONFIG_ID`), with **Client OAuth Login** and **Web OAuth Login**
both turned on. Resolved by the user directly in the Meta Dashboard.
